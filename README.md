# SC26 Reproducibility Artifact

This repository contains the reproducibility artifact for our SC26 paper "Decentralized Scheduling of Scientific Workflows"

The artifact includes the application workload, scheduler configuration, experiment-launch scripts, result extraction and aggregation tools, and scripts required to regenerate the main experimental figures and statistics reported in the paper.

## Artifact Overview

The experiments evaluate a decentralized scheduling approach integrated into COMPSs and compare it with the default hierarchical COMPSs execution model.

The evaluation studies the effect of:

* Number of agents/nodes
* Workflow size, expressed as the number of input-data blocks
* Consensus admission queue size
* Scheduler configuration: decentralized consensus scheduler vs. default scheduler

The main configurations considered in the paper are:

* **Agents/nodes:** 3, 5, 7, 10, and 20
* **Data blocks:** 30, 50, and 100
* **Consensus queue sizes:** 10, 50, 100, and 200
* **Dataset:** Atrial Fibrillation dataset (`7500_100.pickle`)
* **Application:** distributed `GridSearchCV` using Cascade SVM

Single-node executions are additionally used as the reference for parallel-efficiency calculations.

## Repository Structure

```text
sc26_artifact/
├── README.md
├── enqueue
├── analyze
├── fetch_results.py
├── aggregate_results.py
├── generate_figures.py
├── config.properties
│
├── application/
│   ├── gridsearch_csvm.py
│   └── 7500_100.pickle
│
├── dislib/
│   └── ...
│
└── results/
```

### `application/gridsearch_csvm.py`

Contains the GridSearchCV workload used in the experiments.

The application allows the following parameters to be varied:

* Number of hyperparameter combinations
* Number of dataset blocks
* Number of GridSearch executions
* Dataset

The special dataset name `AT` selects:

```text
application/7500_100.pickle
```

### `config.properties`

Configuration file used by the decentralized SwarmTS scheduler.

### `enqueue`

Submits one experiment to COMPSs.

It supports two execution modes:

* `consensus`: decentralized SwarmTS scheduler with plain agents.
* `baseline`: default COMPSs execution using tree agents.

The script automatically stores each experiment under a directory identifying its configuration.

### `fetch_results.py`

Processes the raw COMPSs/SwarmTS output generated by completed experiments.

For each experiment, it produces:

```text
swarm_report.csv
gridsearch_times.csv
```

`swarm_report.csv` contains per-task measurements including consensus, scheduling, execution, retries, conflicts, and protocol-message statistics.

`gridsearch_times.csv` contains the end-to-end GridSearch execution times.

### `aggregate_results.py`

Combines measurements from all experiment configurations found under `results/`.

It generates processed datasets including:

```text
results/processed/experiment_summary.csv
results/processed/efficiency.csv
```

The parallel efficiency is computed as:

```text
efficiency = T1 / (N × TN)
```

where `T1` is the single-node execution time and `TN` is the execution time using `N` agents.

### `generate_figures.py`

Uses the processed CSV files to regenerate the main scalability and scheduler-comparison figures.

Figures are written to:

```text
results/figures/
```

### `analyze`

Runs the complete post-processing pipeline:

```text
raw experiment logs
        ↓
fetch_results.py
        ↓
per-experiment CSV files
        ↓
aggregate_results.py
        ↓
processed CSV files
        ↓
generate_figures.py
        ↓
figures
```

## Software Requirements

The experiments require a COMPSs installation containing the SwarmTS scheduler evaluated in the paper.

The application additionally requires:

* Python 3
* NumPy
* scikit-learn
* dislib
* matplotlib for figure generation

The artifact uses dislib as a Git submodule so that the exact version used for the experiments can be retained.

After cloning the repository, initialize the submodules with:

```bash
git submodule update --init --recursive
```

Alternatively, clone directly with:

```bash
git clone --recurse-submodules <ARTIFACT_REPOSITORY>
```

The precise software versions and commits used for the paper should be preserved by the repository and its submodules.

## Hardware Environment

The experiments reported in the paper were executed on the MareNostrum 5 supercomputer at the Barcelona Supercomputing Center.

Experiments used up to 20 compute nodes.

The artifact is designed so that the project/allocation name and queue/QoS are supplied at execution time and are therefore not tied to the authors' BSC account.

## Running an Experiment

The general syntax is:

```bash
./enqueue <project> <qos> <scheduler> <nodes> \
    [combinations] [blocks] [num_gridsearch] \
    [dataset] [queue_size]
```

For example, a consensus experiment with 5 agents, 30 blocks, and queue size 10 can be submitted with:

```bash
./enqueue <PROJECT> <QOS> consensus 5 9 30 1 AT 10
```

A corresponding baseline experiment can be submitted with:

```bash
./enqueue <PROJECT> <QOS> baseline 5 9 30 1 AT
```

`<PROJECT>` and `<QOS>` must be replaced by values appropriate for the target COMPSs/HPC installation.

## Result Organization

Consensus experiments are stored as:

```text
results/
└── consensus/
    └── q<queue_size>/
        └── b<blocks>/
            └── n<nodes>/
                └── logs/
```

For example:

```text
results/consensus/q10/b30/n5/logs/
```

corresponds to:

* consensus scheduler
* queue size 10
* 30 data blocks
* 5 agents

Baseline experiments are stored as:

```text
results/
└── baseline/
    └── b<blocks>/
        └── n<nodes>/
            └── logs/
```

For example:

```text
results/baseline/b30/n5/logs/
```

## Processing Results

Once one or more experiments have completed, all available results can be processed automatically with:

```bash
./analyze
```

The script discovers the experiments currently available under `results/`; it is therefore not necessary for the complete experimental campaign to be present before running the analysis.

For each experiment, the raw logs are converted into standardized CSV files.

Cross-experiment statistics are then written to:

```text
results/processed/
```

and figures are written to:

```text
results/figures/
```

## Reproducing a Small-Scale Experiment

A small configuration can be used to verify that the artifact and software environment are functioning correctly.

For example:

```bash
./enqueue <PROJECT> <QOS> consensus 3 9 30 1 AT 10
```

After the job finishes:

```bash
./analyze
```

The experiment should produce raw logs, per-task statistics, an end-to-end GridSearch execution time, processed CSV files, and the applicable figures.

This small-scale experiment is intended to exercise the artifact rather than reproduce the complete performance results of the paper.

## Reproducing the Full Evaluation

The complete evaluation requires running the combinations of:

```text
Agents:      3, 5, 7, 10, 20
Blocks:      30, 50, 100
Queue sizes: 10, 50, 100, 200
```

for the consensus scheduler, together with the corresponding baseline experiments.

Single-node experiments for each workload size are required to calculate parallel efficiency.

After all desired experiments have completed, execute:

```bash
./analyze
```

to regenerate the aggregated results and figures.

## Expected Outputs

The artifact produces three levels of output.

### Raw data

```text
results/.../logs/
```

contains the original COMPSs and SwarmTS execution output.

### Extracted and processed data

Each experiment produces:

```text
swarm_report.csv
gridsearch_times.csv
```

Cross-experiment aggregation produces:

```text
results/processed/experiment_summary.csv
results/processed/efficiency.csv
```

### Figures

Paper-related figures are generated under:

```text
results/figures/
```

The plotting scripts operate on the processed CSV files rather than directly on the raw output wherever possible, providing an explicit provenance chain from raw measurements to the reported figures.
